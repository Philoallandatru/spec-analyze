# Base Address Registers (BARs) 详解

**BAR（基址寄存器）是 PCIe 设备向操作系统“声明资源需求并接收物理地址分配”的窗口寄存器**。设备通过 BAR 告诉系统自己需要多大一块内存（或 I/O）空间，系统分配好不冲突的物理地址后写回 BAR，之后 CPU 就能像读写普通内存一样访问设备的寄存器和缓冲区（即 **MMIO**，内存映射 I/O）。

> **直观类比**：BAR 就像新开店铺的“营业执照地址栏”。装修前，店主通过 BAR 申报“我需要一块 16 KB 的地皮”；市政规划局（BIOS/OS）在地图上划出一块空闲地段，把门牌号（如 `0xF8000000`）填回 BAR；此后所有快递员（CPU 读写请求）按这个门牌号就能直接找到店铺柜台（设备寄存器）。

---

## 1. BAR 的位置与三种类型

在 Type 0 配置空间头部（`0x10–0x27`）中共有 **6 个 32 位 BAR 槽位（BAR0–BAR5）**；Type 1 桥接器头部只有 2 个 BAR（`0x10–0x17`）。

| BAR 类型 | 占用槽位 | 地址范围 | 常见用途 |
|----------|----------|----------|----------|
| **32-bit Memory BAR** | 1 个（32 位） | 4 GB 以内（`< 0x1_0000_0000`） | 小型控制寄存器、传统设备 |
| **64-bit Memory BAR** | **2 个连续槽位**（64 位） | 全 64 位物理地址空间 | 现代 NVMe 寄存器、GPU 大显存、CMB |
| **I/O BAR** | 1 个（32 位） | x86 64 KB I/O 端口空间 | 仅用于兼容老式硬件，PCIe 新设备基本弃用 |

---

## 2. BAR 寄存器位域格式

BAR 的最低几位是**只读属性位**（由硬件写死，软件无法修改），高位才是可编程的基地址：

### 2.1 Memory BAR（Bit 0 = 0）

```
31                                        4   3    2   1    0
┌──────────────────────────────────────────┬────┬───────┬───┐
│         Base Address [31:4]              │ Pf │ Type  │ 0 │
│         (至少 16-byte 对齐)              │    │       │   │
└──────────────────────────────────────────┴────┴───────┴───┘
```

- **Bit 0**：`0` 表示 Memory Space。
- **Bits 2:1（Type）**：
  - `00b` = 32-bit 地址空间
  - `10b` = **64-bit 地址空间**（此时当前 `BAR N` 存低 32 位，紧邻的 `BAR N+1` 存高 32 位）
- **Bit 3（Prefetchable）**：`1` = 可预取，`0` = 不可预取。
- **Bits 31:4**：基地址（若为 64-bit BAR，完整地址 = `(BAR[N+1] << 32) | (BAR[N] & ~0xF)`）。

> **示例**：读到 `BAR0 = 0xF800000C`、`BAR1 = 0x00000001`。低 4 位 `0xC` (`1100b`) 表示 Memory(`0`) + 64-bit(`10b`) + Prefetchable(`1`)，完整物理基址为 `0x00000001_F8000000`。

### 2.2 I/O BAR（Bit 0 = 1）

```
31                                                 2   1   0
┌───────────────────────────────────────────────────┬───┬───┐
│            Base Address [31:2] (4B 对齐)          │ R │ 1 │
└───────────────────────────────────────────────────┴───┴───┘
```

x86 下需通过 `in/out` 指令访问，现代 PCIe 设备几乎全部使用 Memory BAR。

---

## 3. Prefetchable vs Non-Prefetchable（关键属性）

Bit 3（Prefetchable）决定了 CPU 和总线控制器能否对这段地址做缓存、合并或提前读取：

| 特性 | Prefetchable（Bit 3 = 1） | Non-Prefetchable（Bit 3 = 0） |
|------|---------------------------|-------------------------------|
| **读操作副作用** | **无副作用**（多次读结果一致，不改变硬件状态） | **可能有副作用**（如读状态寄存器会清中断、弹出 FIFO） |
| **CPU 缓存与预取** | 允许（可映射为 Write-Combining / Cacheable） | **禁止**（通常映射为 Uncacheable，强序执行） |
| **写合并 / 乱序** | 允许（提升大块数据吞吐） | 禁止乱序 |
| **典型应用场景** | GPU 显存（VRAM）、NVMe CMB（控制器内存缓冲区） | 设备控制/状态寄存器、**NVMe Doorbell**、MSI-X Table |

> **为什么控制寄存器不能设为 Prefetchable？** 如果 CPU 提前预取了一个带有“读清零”语义的中断状态寄存器，或乱序合并了两次 Doorbell 写入，就会导致中断丢失或硬件状态错乱。

## 4. BAR 大小探测机制（Sizing）

设备并不会直接写一个“我需要 64 KB”的数字在配置空间里，而是通过**“低位硬连线为 0”**的巧妙机制让系统探测大小：

1. **保存原值**：读取当前 BAR 值并暂存（探测前通常需临时关闭 Command 寄存器的 Memory Space Enable，避免地址冲突）。
2. **写入全 1**：向 BAR 写入 `0xFFFF_FFFF`（如果是 64-bit BAR，同时向 `BAR N+1` 写入 `0xFFFF_FFFF`）。
3. **读回掩码**：硬件只会让“可由软件配置的基地址高位”变成 `1`，对齐所需的低位仍保持 `0`。
4. **取反加一**：清除低 4 位属性位后，按位取反再加 1，即得到空间大小。
5. **恢复原值**（或写入新分配的基地址）。

**计算示例**：
- 写入 `0xFFFF_FFFF` 后读回 `0xFFFF_C000`（清除低 4 位属性后）：
  - 可配置掩码 = `0xFFFF_C000`
  - 大小 = `~0xFFFF_C000 + 1` = `0x0000_4000` = **16 KB**

| 清除低 4 位后的读回值 | 空间大小 | 对齐要求 |
|-----------------------|----------|----------|
| `0xFFFF_FF00` | 256 B | 256 B |
| `0xFFFF_F000` | 4 KB | 4 KB |
| `0xFFFF_0000` | 64 KB | 64 KB |
| `0xFFF0_0000` | 1 MB | 1 MB |
| `0xFF00_0000` | 16 MB | 16 MB |

## 5. 系统启动时的 BAR 分配与物理地址布局

```
物理地址空间（x86_64 示例）
0xFFFF_FFFF_FFFF_FFFF ┌─────────────────────────────┐
                      │  64-bit PCIe MMIO 空间       │ ◀── 64-bit BAR（如大显存、现代 NVMe）
0x0000_0001_0000_0000 ├─────────────────────────────┤ (4 GB 界线)
                      │  32-bit PCIe MMIO 洞         │ ◀── 32-bit BAR（必须放在 4GB 以下）
0x0000_0000_C000_0000 ├─────────────────────────────┤
                      │  系统内存 (System RAM)       │
0x0000_0000_0000_0000 └─────────────────────────────┘
```

1. **BIOS/UEFI 阶段**：枚举总线、探测每个 BAR 大小、在不与系统 RAM 冲突的 MMIO 区间内分配基地址并写入 BAR。
2. **OS 内核阶段**：检查资源树（`/proc/iomem`），对未分配或冲突的 BAR 重新分配，并配置沿途 Type 1 桥接器的转发窗口。
3. **驱动加载阶段**：调用 `pci_enable_device_mem()` 开启 Command[Memory Space Enable]，再用 `ioremap()` 将 BAR 物理地址映射为内核虚拟地址，即可通过 `readl`/`writel` 访问设备寄存器。

> **扩展特性 — Resizable BAR（可调整 BAR）**：传统 BAR 大小在硬件出厂时写死，而扩展能力 `0x0013`（Resizable BAR）允许显卡等设备向系统申报多个可选容量（如 256 MB ~ 16 GB），由 OS 根据可用 64-bit MMIO 空间动态放大 BAR，从而让 CPU 一次性直接访问全部显存。

## 6. 实用 CLI 调试命令

```bash
# 1. 查看设备所有 BAR 的地址、位宽、预取属性与大小
lspci -vvv -s 01:00.0 | grep "Region"
# 示例: Region 0: Memory at f8000000 (64-bit, non-prefetchable) [size=16K]

# 2. 查看内核为设备分配的物理地址范围
cat /proc/iomem | grep -A 2 "0000:01:00.0"

# 3. 查看 sysfs 中记录的 BAR 资源（start  end  flags）
cat /sys/bus/pci/devices/0000:01:00.0/resource

# 4. 用 setpci 读取 BAR0 原始十六进制值（偏移 0x10）
setpci -s 01:00.0 10.l
```

> **提示**：不要在设备驱动正在运行时用 `setpci` 向 BAR 写入 `0xFFFFFFFF` 探测大小，这会导致正在进行的 MMIO 访问瞬间失效甚至引发系统崩溃。

## 关联与引申概念

| 概念 | 简要说明 | 相关文档 |
|------|----------|----------|
| **MMIO vs DMA** | BAR 实现的是 **MMIO**（CPU 主动读写设备寄存器）；而设备主动读写主机内存则依靠 **DMA**（需开启 Command[Bus Master]）。 | [配置空间详解](config-space.md) |
| **Type 0 vs Type 1** | Type 0 提供 6 个 BAR；Type 1 桥接器通过 Memory Base/Limit 窗口将上游的 BAR 访问转发给下游设备。 | [头部类型详解](header-types.md) |
| **MSI-X Table & PBA** | MSI-X 的中断向量表（Table）和挂起位数组（PBA）就存放在设备 BAR 映射的内存中，由 BIR 字段指明所在 BAR 编号。 | [MSI-X 详解](../interrupts/msix.md) |
| **Resizable BAR** | 位于扩展配置空间（`0x100+`）的能力结构，允许动态修改 BAR 容量以释放大显存访问性能。 | [扩展能力详解](extended-capabilities.md) |
