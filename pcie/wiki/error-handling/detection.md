# PCIe 错误检测机制

**PCIe 错误检测**是在物理层、数据链路层和事务层逐级设置的“安检关卡”。就像跨国快递要经历“物流安检（物理线路）→ 站点封签核对（逐跳链路）→ 收件人开箱验货（端到端事务）”，每一层只负责检查自己关心的完整性，确保比特翻转、丢包、乱序或格式违规能在第一时间被发现并拦截。

---

## 三层纵深检测架构

```
上层应用 / 驱动
      ▲
┌─────┴──────────────────────────────────────────────────┐
│ Transaction Layer（事务层：端到端检查）                  │
│  • TLP 格式与对齐验证（Malformed TLP 检测）              │
│  • ECRC（32-bit 端到端 CRC，可选，穿越 Switch 保持不变）  │
│  • EP 位检查（Poisoned TLP 识别）                       │
└─────▲──────────────────────────────────────────────────┘
      │
┌─────┴──────────────────────────────────────────────────┐
│ Data Link Layer（数据链路层：逐跳可靠性检查）             │
│  • LCRC（32-bit 链路 CRC，覆盖 Seq# + TLP）             │
│  • 12-bit 序列号检查（检测丢包、重复、乱序）              │
│  • DLLP 16-bit CRC 校验                                │
└─────▲──────────────────────────────────────────────────┘
      │
┌─────┴──────────────────────────────────────────────────┐
│ Physical Layer（物理层：比特与符号级检查）                │
│  • Gen1/2：8b/10b 非法符号与极性（Disparity）检查        │
│  • Gen3+：128b/130b Sync Header 锁定与加扰同步          │
└─────▲──────────────────────────────────────────────────┘
      │
  PCIe 差分链路
```

## 一、物理层错误检测

物理层直接面对高速串行电信号，主要防范噪声、衰减和时钟漂移导致的比特误码。

### 1. Gen1 / Gen2：8b/10b 编码检测
在 PCIe 1.0（2.5 GT/s）和 2.0（5.0 GT/s）中，每 8 位数据会被编码为 10 位物理符号传输，以保证直流平衡（0 和 1 数量大致相等）和足够的电平跳变供时钟恢复。接收端会持续检查：
- **非法符号（Invalid Symbol）**：收到的 10-bit 码字不在合法映射表内（例如连续 10 个 `1`）。
- **极性错误（Running Disparity Error）**：8b/10b 要求链路正负极性交替平衡；若当前期望负极性符号却收到正极性版本，即判定出错。
- **控制字符错位**：将专用控制符号（K 码，如链路训练/帧界定符）错误地当成普通数据接收。

### 2. Gen3+：128b/130b 编码检测
从 PCIe 3.0（8.0 GT/s）起，为降低 20% 的编码开销，改用 **128b/130b** 编码（每 128-bit 载荷前仅加 2-bit **Sync Header**）：
- **Sync Header 校验**：合法的 Sync Header 只能是 `01b`（数据块）或 `10b`（控制序列块 Ordered Set）。若收到 `00b` 或 `11b`，说明发生误码或边界失步。
- **块锁定（Block Lock）状态机**：若连续多个数据块均未检测到合法 Sync Header，接收端会判定**失去块锁定**，从 `Lock` 退回 `Search` 重新对齐；同时配合 **LFSR（线性反馈移位寄存器）加扰/解扰器** 同步校验。

> **处理结果**：上述物理层异常统一记入 AER 的 **Receiver Error（可纠正错误）**；物理层尝试重同步，若误码率超过阈值则触发链路重训练（Link Retrain）。

## 二、数据链路层错误检测

数据链路层负责**相邻两个端口之间（逐跳，Hop-by-Hop）**的无差错传输，核心工具是 **LCRC**、**序列号** 和 **DLLP CRC**。

### 1. LCRC（Link CRC，链路层 32-bit 校验）
每发送一个 **TLP**，数据链路层都会在其头部加上 2 字节的 **Sequence Number（序列号）**，并在尾部附上 4 字节的 **LCRC**：

```
+-------------+--------------+-----------------+--------------+
| Start Token | Seq# (2 B)   |   TLP 内容      |  LCRC (4 B)  |
+-------------+--------------+-----------------+--------------+
              └────────── LCRC 计算覆盖范围 ─────────┘
```

- **出错处理**：若接收端重算 LCRC 不匹配，立即丢弃该 TLP，**不发送 ACK**（并可发送 **NAK DLLP**）。发送端的重传定时器（Replay Timer）超时或收到 NAK 后，会从 **Retry Buffer（重试缓冲区）** 自动重传该 TLP，对上层软件完全透明。

### 2. 12-bit 序列号检测（0 ~ 4095 循环）
每个 TLP 都携带单调递增的 12 位序列号，接收端据此识别三类异常：

| 收到序列号 vs 期望值 | 判定结果 | 接收端动作 |
|---------------------|---------|-----------|
| `Seq == 期望值` | 正常顺序到达 | 接收 TLP，期望值 `+1`，回复 **ACK DLLP** |
| `Seq > 期望值`（跳号） | 中间发生丢包 | 丢弃当前包，向对端发送 **NAK（期望值）** 请求重传 |
| `Seq < 期望值`（回退） | 重复包或重传包 | 若尚未确认则接收，若已确认过则直接丢弃（去重） |

### 3. DLLP CRC-16 检测
**DLLP（Data Link Layer Packet）** 仅在相邻链路两端之间传递（用于 ACK/NAK、流控信用 UpdateFC、电源管理 PM_Enter_L1 等），固定 6 字节，尾部携带 **16-bit CRC**。若校验失败则直接丢弃并记为 **Bad DLLP（可纠正错误）**，由于 DLLP 携带的状态会被后续周期报文刷新，因此无需重传机制。

## 三、事务层错误检测

通过链路层安检后，TLP 进入事务层进行端到端的语义与完整性核验。

### 1. ECRC（End-to-End CRC，端到端 32-bit 校验）
**LCRC 只管“这一跳”**：当 TLP 经过 PCIe Switch 时，Switch 会剥掉旧的 Seq# 和 LCRC，修改路由信息后再重新计算下一跳的 LCRC。如果 Switch 内部缓存发生了比特翻转，LCRC 是查不出来的。

为此，PCIe 在 AER 中提供了可选的 **ECRC**：

```
+--------------+---------------+--------------+
|  TLP Header  | Data Payload  |  ECRC (4 B)  |
+--------------+---------------+--------------+
└────── ECRC 计算覆盖范围 ──────┘
(发送端生成，中间 Switch 不修改也不校验，终点接收端校验)
```

- 只有当请求端和接收端都在 AER Capability Control（`+0x18`）中启用了 **ECRC Generation / Check**，且 TLP 头部的 `TD`（TLP Digest）位置 `1` 时才会生效。校验失败上报 **ECRC Error**。

### 2. TLP 格式与合法性验证（Malformed TLP）
接收端会严格校验 TLP 头部字段的一致性，包括：
- `Fmt` 与 `Type` 编码是否为规范定义值；
- `Length` 字段（单位 DW，1~1024）是否与实际收到的 Data Payload 长度一致；
- Memory 请求的地址与 `First/Last BE`（字节使能）是否符合对齐规则；
- 配置请求（Type 0/1）的寄存器偏移与 BDF 范围是否合法。

一旦违反上述规则，立即判定为 **Malformed TLP**（默认致命错误），丢弃数据包并记录到 AER Header Log。

### 3. Poisoned TLP 检测（`EP` 位）
TLP Header 中的 **EP（Error Poisoned）** 位用于“主动标记坏数据”。例如设备响应读请求时内部发生不可纠正 ECC 错误，设备不会伪造假数据，而是把 `EP` 设为 `1` 继续发回 Completion。接收端检测到 `EP=1` 后，立即记录 **Poisoned TLP Received** 并将错误隔离上报给 CPU/驱动。

## 接收路径检测顺序与性能开销

在一个硬件接收流水线中，上述检测通常按**从外到内（或并行流水）**的顺序执行：

```
物理信号进入 ──▶ 1. 物理层解码 (8b/10b 或 128b/130b) ──[错]──▶ Receiver Error
                       │ OK
                       ▼
                 2. LCRC 校验 + 序列号检查 ───────────[错]──▶ 丢弃 + 发 NAK（链路层重传）
                       │ OK (回复 ACK)
                       ▼
                 3. TLP 格式验证 ─────────────────────[错]──▶ Malformed TLP（上报 AER）
                       │ OK
                       ▼
                 4. ECRC 校验（若启用且 TD=1）────────[错]──▶ ECRC Error（上报 AER）
                       │ OK
                       ▼
                 5. EP 位检查（Poisoned?）────────────[是]──▶ Poisoned TLP（隔离并上报）
                       │ 否 (EP=0)
                       ▼
                 交付上层处理
```

| 检测机制 | 典型硬件延迟 | 带宽开销 |
|---------|-------------|---------|
| 8b/10b 解码（Gen1/2） | < 1 ns | 20% 编码开销（Gen3+ 128b/130b 降至 ~1.5%） |
| LCRC + 序列号 | 2 ~ 5 ns | 每个 TLP 固定 +6 字节 |
| ECRC（可选） | 5 ~ 10 ns | 每个 TLP 固定 +4 字节 |
| TLP 格式校验 | 1 ~ 2 ns | 0 字节 |

### Linux 内核事件追踪

在支持 ftrace 的 Linux 系统上，可以通过内核追踪点实时观察错误检测与 AER 事件：

```bash
# 录制 PCIe 与 AER 追踪事件
trace-cmd record -e aer:aer_event
# 查看记录报告
trace-cmd report
```
