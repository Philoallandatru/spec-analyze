# 持久事件日志（Persistent Event Log）

## 一句话说明

持久事件日志（`LID 0Dh`）是 NVM 子系统级别的**跨断电事件历史**：通过"**建立报告上下文 → 多次分段读 → 代数一致性校验**"的三段式流程，让多个主机在不一致的访问时序下都能读到一致的事件快照。

## 生活化类比

把持久事件日志想成**酒店的"事件档案柜"**：

- **柜子里的所有档案 = 持久存储的事件**（断电也不丢）。
- **"我今天想看哪些档案" = 报告上下文（Reporting Context）**：你**建立那一刻**，档案员把"当前档案清单"拍成一张**照片（快照）**给你。
- **分多次抄录 = 多次 `Get Log Page` 读取**：因为档案太多，一页抄不完，分几次来。
- **校验码 = 代数编号（Generation Number）**：你抄前抄后都要看一眼"这张照片的版本号"——如果中途有人**更换了照片**（建立新上下文），你抄到的就是**不同快照**拼起来的"弗兰肯斯坦"，**必须重来**。
- **释放 = 交还快照**：要么你主动释放，要么超时/复位自动释放；其他人才能"建下一张快照"。

档案是**只增不改**的，新事件一直写进柜子，**但不会进入当前快照**——所以你这次读到的清单**不会**因为"边读边有新事件"而变得前后不一致。

## 工作流程

```text
   事件发生 -> 持久存储
                  |
                  v
         +---------+----------+        +---------+----------+
         |  报告上下文建立     |  ----> |  多次 Get Log Page   |
         |  (Establish)        |       |  按字节偏移读        |
         +---------+----------+        +----------+---------+
                   |                              |
                   |         代数检查              |
                   |<----- 头/尾代编号对比 --------|
                   |                              |
              Release / 复位 / 超时             释放上下文
```

简化说明：上图省略事件类型分布、UUID 过滤与厂商扩展，专注"建立—读—校验—释放"主流程。

### 上下文状态机

| 状态 | 描述 | 允许的操作 |
|------|------|----------|
| 无上下文 | 初始态或已释放 | 仅可建立 |
| 上下文存在 | 已建立快照 | 可读、可检查、可释放 |
| 已释放 | 主动或被动释放 | 回到"无上下文" |

### 上下文操作矩阵

| 操作 | 行为 |
|------|------|
| Read | 读取快照；要求上下文已存在，否则返回 Command Sequence Error |
| Establish and Read | 冻结事件长度与集合并返回请求偏移的数据；**已存在上下文则失败** |
| Release | 删除上下文；不返回数据；**幂等** |
| Establish/Check Header | 总是返回 512 字节头，并报告上下文是否已存在 |

### 自动释放条件

- 主机显式 `Release`。
- NVM 子系统重置。
- 控制器级重置。
- 厂商超时（通常足够完成正常检索）。

## 初学者案例

**场景：审计员拉取 6 个月的子系统事件**

1. 审计员提交 `Get Log Page(LID=0Dh, Action=Est&Read, Offset=0)` 建立上下文并读头。
2. 控制器返回 512 字节头部：含 `TNEV`（事件总数）、`TLL`（总字节数）、`Generation Number`（**G₁**）。
3. 审计员分多次 `Get Log Page` 偏移读取剩余字节，直到 `TLL` 全部读完。
4. 再次读头比较 `Generation Number`：
   - 仍是 `G₁` → 数据完整有效。
   - 变为 `G₂` → 期间**有新的建立动作**导致快照更换；本次数据**无效**，**重新建立**再来。
5. 校验通过后，审计员 `Action=Release` 释放上下文；其他人可建立新快照。
6. 若中途忘记释放，厂商超时后系统也会自动释放，**不会**永久卡住。

> 故障速查：代数不一致 = "我读着读着有人换了照片"，**不要**靠补读对齐；**整段重来**。

## 必须记住的规则

| 规则 | 要点 |
|------|------|
| 跨断电 | 事件**断电后仍保留**；上下文本身可被重置/超时释放 |
| 子系统级 | 整个 NVM 子系统共享**同一份**事件历史 |
| 一致性快照 | 上下文建立时**冻结**事件集合与长度；后续事件**不进**当前快照 |
| 三段式 | 主机负责"建立→分次读→代数校验"；不能假设单次 Get Log Page 能读完 |
| 代数协议 | 头/尾的 Generation Number 不一致 → 整批数据作废，**重新读** |
| Action 互斥 | "建立"与"读"是不同 Action；已存在上下文时建立类操作失败 |
| Release 幂等 | Release 不存在上下文也成功；不返回数据 |
| 自动释放 | 显式 Release、子系统复位、控制器级复位、厂商超时都释放上下文 |
| 抑制规则 | 控制器对**重复事件**可按厂商频率阈值抑制；满/超限时执行厂商删除策略 |
| 多控制器一致性 | 同一事件若影响多控制器，**仅由厂商选定的其中一个**记录 |
| Sanitize 联动 | 执行 Sanitize 可能删除或修改事件记录（防止历史泄露） |
| `ECRH` 能力 | 修订版 2.1 控制器公布 `ECRH` 能力位以表明支持建立/检查头与代数协议 |

## 容易混淆的地方

| 容易混 | 实际区别 |
|--------|----------|
| 持久事件日志 vs SMART | 一个是"事件历史"（按发生时间），一个是"当前+终生健康"（按度量值） |
| 持久事件日志 vs Telemetry | Telemetry 是"详细诊断数据块"；本日志是"事件条目流" |
| 上下文存在 vs 数据有效 | 上下文存在只代表"有快照"；数据是否有效还需**代数校验** |
| `Release` vs 自动释放 | Release 是主动；超时/复位是被动；行为等价 |
| 代数不变 vs 代数改变 | 代数**仅**在新建且数据不同才递增；同样事件集不会让代数变 |
| `TNEV` vs `TLL` | 事件数量 vs 字节总数；二者**不必等比例**（事件长度可变） |
| 事件 vs 错误条目 | 错误条目在 Error Information（`LID 01h`）；持久事件是更广义的子系统事件 |
| `Establish` vs `Establish&Read` | 前者只建快照不返回数据；后者建立并立即读 |
| UUID 过滤 | 厂商事件可按 UUID 索引过滤；通用事件**总是**包含 |
| 多 Event Type 版本 | Event Type Revision 与 Log Revision 独立演进 |

## 进阶细节

- **快照头部（512 字节）关键字段**：`LID`（恒为 `0Dh`）、`TNEV`、`TLL`、`LREV`（应为 `03h`）、上下文建立时间、电源历史、控制器 ID、子系统 NQN、`Generation Number`、Reporting Context Information、Supported Events Bitmap。
- **Reporting Context Information** 包含：上下文存在标志、建立端口类型（子系统端口 vs Management Endpoint）、建立端口 ID。
- **Supported Events Bitmap** 位编号 = 事件类型号，涵盖：SMART/Health 快照、固件、时间戳与重置、硬件错误、命名空间变更、Format/Sanitize、Feature 变更、Telemetry 创建、温度异常、介质验证、厂商特定、TCG 定义。
- **事件条目通用结构**：事件头（类型、版本、`EHL`、控制器 ID、时间戳、端口关联、厂商信息长度 `VLI`、事件数据长度 `EL`） + 可选厂商信息 + 类型特定数据。头部长度 = `EHL + 3`；`EL` 涵盖可选厂商信息与类型特定数据。
- **端口关联类型**：子系统端口 / Management Endpoint / 无端口关联。
- **基础必记事件类型**：
  - SMART/Health 快照：每个控制器**至少每 24 个通电小时**一次；虚拟化下每个主控制器一次。
  - 固件提交：旧/新版本、操作、槽位、完成状态、可选厂商结果。
  - 时间戳变更：先前时间戳 + 自 CLR 以来毫秒数；当前时间戳在通用事件头。
  - 上电/重置：生效固件版本 + 每控制器重置描述符（含 NVM 格式操作状态、上电毫秒数等）。
- **NVM 子系统硬件错误（事件类型 `05h` / 版本 `02h`）附加信息**：
  - PCIe 可纠正 / 不可纠正非致命 / 不可纠正致命：AER 状态、错误掩码、TLP 头/前缀日志。
  - PCIe 链路状态变更：链路状态寄存器。
  - PCIe 链路未激活：无附加信息。
  - 警告事件：警告位图 + 可选 Endurance Group ID。
  - 意外断电：生命周期断电次数 + 带外原因标志。
  - 致命控制器状态：状态信息。
  - 介质/数据完整性错误：捕获的 CQE。
  - 控制器就绪超时：CNR 状态、Admin 介质未就绪、NS 未就绪、所选 CRIME 模式。
- **配对记录（破坏性操作）**：Format NVM 与 Sanitize 都有"开始"和"完成"两条事件——开始记录意图（参数、验证 NSID 等），完成记录结果（最小进度、未完成标志、CQE 状态、厂商结果）。
- **Set Feature 事件**：仅在受支持且可记录的 Feature 通过 Set Features 成功变化时记录；事件载荷长度可变（CDW10 起保留多少 dword + 可选完成 Dword 0 + 内存缓冲字节数）。
- **温度事件细节**：高温警告/临界阈值跨越、节流开始/停止、返回正常；低温阈值跨越——均受厂商频率抑制。
- **厂商事件结构**：一份或多份描述符，每份带事件代码 + UUID 索引 + 类型化数据（名称 / ASCII / 二进制 / 有符号整数）；名称描述符排在首位；同一事件代码下名称稳定。
- **TCG 定义事件**：事件版本 + 保留给 TCG 的载荷。
- **代数编号的变化条件**：仅在新建上下文且返回**不同数据**时递增；同样事件集合重复读不会改代数。
