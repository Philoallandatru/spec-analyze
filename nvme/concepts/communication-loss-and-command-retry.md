# 通信丢失与命令重试

## 一句话说明

通信丢失（Communication Loss）是一段"主机不知道控制器还在不在、控制器不知道主机还在不在"的危险时期；NVMe 用一套"先停止、再分类、最后重试"的流程保证：要么明确知道原命令已不可能执行、要么把决策权交给上层。

## 生活化类比

想象你在**快递柜**上发起了一次寄件，但手机突然断网、柜机也黑屏了：

- **断网** = 通信丢失
- **寄件指令到底执行了没** = 不确定
- 快递员不能立刻再投一次，因为：
  - 第一次可能根本没投成功（可重投）
  - 第一次可能已成功但柜机没回执（重投会产生重复包裹）
  - 第一次可能是改地址这种"做完就毁"的非幂等操作（重投会出错）

NVMe 的解决思路：
1. **等够长的时间**（建立"停止屏障"），让原来的指令无论成败都尘埃落定
2. **按指令性质分三类**（无限制 / 延迟 / 状态依赖）选择不同的"再投"策略
3. **多主机场景下必须用专用机制**（Reservations / Compare and Write）而不是普通读写来协调

## 工作流程

```text
+---------------------- 通信丢失发生 ----------------------+
|                                                          |
|  主机侧:                                                 |
|  1) 终止 Association / 传输连接（Fabrics）                |
|  2) 等待控制器侧检测:                                    |
|     - Command 模式: 2 × KATT                             |
|     - Traffic 模式: 3 × KATT                             |
|     - 或接收传输层丢失通知                                |
|  3) 等待命令停止:                                        |
|     - CQT ≠ 0  时等 CQT                                  |
|     - CQT = 0  时等实现特定时长                           |
|                                                          |
|  [停止屏障建立完成]                                      |
|                                                          |
|     +-----------------+----------------+----------------+
|     |                 |                |
|     v                 v                v
+-------------+    +-------------+   +-------------------+
|  无限制重试 |    |  延迟重试   |   |  状态依赖重试     |
|  (Unrestricted) | (Delayed)  |   | (State-Dependent) |
+-------------+    +-------------+   +-------------------+
```

**重试分类核心条件**：

| 类别 | 幂等性 | 影响范围 | 命令效果位 |
|------|--------|---------|-----------|
| 无限制重试 | 幂等 | 仅辅助状态 | `CCC=0 ∧ NIC=0 ∧ NCC=0 ∧ LBCC=0` |
| 延迟重试 | 幂等 | 用户数据 / 子系统状态 | 不强制全 0 |
| 状态依赖重试 | 非幂等或影响其他主机 | 跨主机或跨命名空间 | 至少一位非 0 |

## 初学者案例

**场景：写一个 4 KiB 块到 NVMe-oF 设备，链路中断后能否重试？**

1. 主机通过 RDMA 提交 `Write` 到 LBA 0x1000。
2. 完成响应丢失，主机进入 communication-loss 流程。
3. 等待 `2 × KATT`（=240 s）+ `CQT`（非 0 时），确保控制器已停止处理原命令。
4. **因为是单主机、对确定地址的写入**，属于"延迟重试"：
   - 不能立即向上层报告成功
   - 必须等到"原命令 + 所有重试"都不再可能执行
   - 才能把重试结果返回给文件系统
5. 若上层文件系统**已基于写完成的假设提交了后续写**，则这次延迟必须覆盖到后续写完成之后。

> 关键收获：即使命令本身"幂等"，NVMe 仍按"延迟重试"对待，因为上层软件的顺序依赖使得"过早暴露重试成功"会破坏数据一致性。

## 必须记住的规则

| 规则 | 要点 |
|------|------|
| 停止屏障三阶段 | 断连 → 等待控制器检测 → 等待命令停止，缺一不可 |
| 2×KATT 假设 | 假设传输最多延迟 1 个 KATT + 控制器检测 1–2 个 KATT |
| CQT 决定宽限 | `CQT ≠ 0` 时用 CQT；`CQT = 0` 时用实现特定时长 |
| 数据完整性不变式 | 介质/读/内部错误时，与失败命令相关的传输数据**不得**作为有效数据 |
| 优先 Controller Reset | 先用 Controller Reset；失败且支持时才用 NVM Subsystem Reset（NSSR）|
| NSSR 风险 | NSSR 会导致 PCIe Link Down，对 FFH 等环境不安全 |
| 后台操作可穿越 | Sanitize 等后台操作可能在通信丢失后继续，需用其他控制器跟踪 |
| 状态依赖不可下放驱动 | 非幂等 / 跨主机影响命令必须由上层软件决策 |

## 容易混淆的地方

| 容易混 | 实际区别 |
|--------|----------|
| KATT vs CQT | `KATT` 是 Keep Alive 心跳间隔；`CQT` 是超时后清理命令队列的宽限 |
| 停止屏障 vs 立即重试 | 停止屏障是"先确保原命令不再执行"；没有屏障的重试是赌博 |
| 幂等 vs 无副作用 | 幂等是"重复执行结果相同"；无副作用是"不改变子系统状态"；二者不同 |
| Command 模式 vs Traffic 模式 | 决定了 KATT 倍数（2 vs 3）以及最坏超时延迟 |
| 跨控制器路径 vs 跨主机路径 | 前者是同一主机通过不同控制器；后者是不同主机，应使用 Reservations |
| Controller Reset vs NSSR | 前者仅复位控制器；后者复位整个 NVM 子系统（含 PCIe 链路） |

## 进阶细节

- **错误严重度阶梯**（规范 6.2.1）：
  1. 普通命令错误 → 看 CQE 的 `CRD` 位决定是否重试
  2. 严重队列错误 → 删 SQ/CQ（删 SQ 中止所有未完成命令）
  3. 控制器级严重错误 → Controller Level Reset
  4. 致命错误（`CSTS.CFS=1`） → Controller Reset，失败再考虑 NSSR
- **CQT 默认值**（规范 6.2.2）：PCIe 默认 `CQT=0`（实现特定）；Fabrics 强制非零以容纳异步链路丢失。
- **跨控制器路径风险**（规范 6.2.3）：在控制器 1 上的延迟重试 Write，可能在控制器 2 看来"已完成"，从而被上层视作确认；这会破坏写后写顺序，必须延迟到控制器 1 也停止后才能暴露。
- **多主机语义**（规范 6.2.4）：在多主机拓扑中，单主机的停止屏障不足以保护其他主机；需要 Reservations 或 Compare and Write 强制串行。
- **保守降级**（规范 6.2.5）：主机可主动把"无限制"降级为"延迟"或"状态依赖"，把"延迟"降级为"状态依赖"，以安全换效率。
- **后台操作追踪**（规范 6.2.6）：Sanitize / Format NVM / Firmware Update 等长操作在通信丢失后不会自动取消；驱动需通过其他控制器或重新发现继续轮询。
- **重试结果暴露窗口**（规范 6.3）：延迟重试的结果必须等"原命令 + 之前所有重试"都完成或已可证明不会完成后才能暴露。
- **Reservation 配合**（规范 8.1）：状态依赖重试建议配合 Reservation 类型 1/2/3/4 串行化访问，避免跨主机覆盖。
