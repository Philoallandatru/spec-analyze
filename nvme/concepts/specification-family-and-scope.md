# 规范族与适用范围（Specification Family and Scope）

## 一句话说明

NVMe 不是一本规范，而是一族分工明确的规范文档：基础规范定义与传输无关的协议，I/O 命令集、传输、管理、引导各成一份独立规范，共同保证主机软件与 NVM 子系统互操作。

## 生活化类比

把 NVMe 规范族想成**一栋写字楼的"物业管理 + 部门职责"手册**：

- **基础规范** = 楼宇总规（约定了大堂、电梯、走廊怎么走，所有公司都要遵守）
- **I/O 命令集规范** = 各入驻公司的部门规章（NVM 部门、键值部门、分区部门各自追加细节）
- **传输规范** = 楼内布线（PCIe、RDMA、TCP、光纤通道，各走各的物理通道）
- **NVMe-MI 规范** = 物业办公室的接口（带外管理，房东不进大堂也能远程抄表）
- **引导规范** = 大楼门口的迎宾流程（怎么引导新住户第一次进门——也就是系统从这块盘启动）

关键一点：手册之间是**适用关系**而不是**层级关系**——总规不能凌驾于部门规章之上，部门规章也不能反过来覆盖总规；遇到冲突时各管各的范围。

## 工作流程

```text
   I/O 命令集规范                传输规范
   (NVM / KV / ZNS)             (PCIe / RDMA / TCP / FC)
         |                            |
         |  扩展                       |  绑定
         |                            |
         +----->  NVMe 基础规范 <-----+
                  (与传输无关的核心协议)
                  /          |          \
                 /           |           \
          NVMe-MI        引导规范       适用范围:
          (管理接口)    (启动流程)     各规范平行协作
```

要点：图中的箭头表示"适用范围"，不是协议分层。各规范是平级协作，遇到具体场景（如"PCIe 上的 NVM 盘"）时三本规范被同时参考。

## 初学者案例

**场景：你想给一块消费级 NVMe SSD 写驱动，该读哪本规范？**

1. 先打开**基础规范**第 1 章，确认 NVMe 的整体工作模型和命令格式。
2. 因为是消费级 PCIe 盘，**传输规范**要选 NVMe over PCIe（TP-4xxx 章节，PCIe 寄存器映射、PRP/SGL 等）。
3. 你的盘是普通块设备，就只读**NVM 命令集规范**，不必看 Key Value 或 ZNS。
4. 如果只是做主机端驱动，**NVMe-MI** 和**引导规范**可以先跳过——前者给带外 BMC 用，后者给 BIOS/UEFI 工程师用。

排错思路：当你看到一份文档说"参考 section 3.1.3"或"CC.EN=1"时，这是基础规范的内容；看到"MRd/TLP"是 PCIe 传输规范；看到"zone append"是 ZNS 命令集——把规范族想成分工，迷路时按"我在哪一层"定位。

> 速记：读规范的第一条规矩——**先认章节属于哪本规范，再看细节**。

## 必须记住的规则

| 规则 | 要点 |
|------|------|
| 五类规范协作 | 基础 + I/O 命令集 + 传输 + NVMe-MI + 引导规范，互相是"适用"关系 |
| 基础规范定义协议 | 主机软件与 NVM 子系统之间、与传输无关的通信协议 |
| 传输规范做绑定 | 把基础规范的协议绑定到具体传输（PCIe、RDMA、TCP、FC） |
| 命令集规范做扩展 | 在基础规范之上追加 NVM / Key Value / ZNS 等命令与数据结构 |
| NVMe-MI 是带外管理 | 可选的、与主机驱动并行的设备管理接口 |
| 引导规范管启动 | 定义从 NVMe 设备引导系统的构造和指南 |
| 范围之内 | 控制器的属性与行为、管理与 I/O 命令、命令集共有特性、主机控制器交互 |
| 范围之外 | SSD/主存/缓存/备份/冗余等使用模型、磨损均衡与擦除算法、缓存策略 |
| mandatory / shall | 强制要求，关系到一致性和互操作 |
| may | 允许选择，无偏好 |
| optional | 可选功能，若实现则必须按规范定义 |
| should | 强烈建议（"推荐"），除非有充分理由否则应遵循 |
| obsolete | 早期版本有、当前已删除（保留字面以兼容旧文档） |
| 保留字段写入 | 必须清零；读到保留值要忽略；收到保留编码应报错误 |
| 数值 1-based | 默认 1h=1，未特别说明时**不是** 0-based |
| 单位 | 二进制用 Ki/Mi/Gi，10 进制用 k/M/G（图见规范 Figure 2） |
| ASCII 字符串 | 仅允许 20h–7Eh，左对齐，必要时右侧补空 |

## 容易混淆的地方

| 容易混 | 实际区别 |
|--------|----------|
| 规范族 vs 规范分层 | 规范族是平行协作的"分工手册"，不是 TCP/IP 那种协议栈 |
| 基础规范 vs 命令集规范 | 基础规范是"所有命令集的公约数"；命令集规范是"某个命令集的扩展" |
| 基础规范 vs 传输规范 | 基础规范定义**协议**；传输规范定义**物理/逻辑传输**上的绑定 |
| 范围之内 vs 范围之外 | 范围之外不是"不重要"，而是"实现者自由发挥"（如 SSD 内部 FTL） |
| mandatory vs optional | mandatory 必须实现；optional 可不实现，但**一旦实现就必须按规范** |
| shall vs should | shall 是强制的；should 是"推荐"，技术上可违反但需充分理由 |
| 保留字段 vs 私有扩展 | 保留字段必须清零且不能依赖；私有扩展走厂商特定路径，不占保留位 |
| 0-based vs 1-based | 规范默认 1-based；只有特别注明（如某些计数寄存器）才用 0-based |
| 主机端 vs 控制器端 | 关键字对双方要求不同（如 shall 写保留字段 = 主机必须清零；控制器不要求校验） |

## 进阶细节

- **三类控制器**（规范 1.2）：I/O 控制器、Discovery 控制器、Administrative 控制器；"控制器"一词在多数上下文指 I/O 控制器，但其他两类在 Fabrics 场景同样存在。
- **范围之内的细项**（规范 1.2）：
  - 与 NVM 子系统中控制器通信所需的属性集合
  - 由某 NVMe Transport 实现的控制器实例
  - 各 I/O 命令集共有特性
- **范围之外的细项**（规范 1.3）：
  - 具体使用模型：SSD / 主存 / 缓存 / 备份 / 冗余——只定义通信接口，不规定用途
  - 实现方式：直连 fabric 的 SSD、fabric↔PCIe 网关设备、通用服务器上的软件实现
  - 介质管理细节：磨损均衡、擦除等被抽象
  - 缓存算法/技术
  - 其他已发布规范本身的实现（如 PCI、PCIe、PCI-X 本身）
- **保留字段的硬规则**（规范 1.4.1.6）：
  - 保留位/字节/字/字段/属性/寄存器**必须清零**，或按未来扩展处理
  - 接收方**不需要**校验保留位是否被清零
  - 在已定义字段中收到保留编码值**应报错**
  - 向控制器属性字段写入保留编码值 = **未定义结果**
- **缩写约定**：图表空间不足时用 `R` 代替 "reserved"。
- **二进制单位幂**（规范 Figure 2）：kibi/Ki=2^10，mebi/Mi=2^20，gibi/Gi=2^30，依此类推到 yobi/Yi=2^80。
- **Figure 1 关键约束**：规范族图只表示"适用范围"，**不表示层级、协议栈或系统架构**——这是被反复强调的设计意图。
- **规范版本号定位**：从 2.0 到 2.1 的变更清单在 nvmexpress.org/changes；2.1 新增的能力是控制器合规的强制要求。
