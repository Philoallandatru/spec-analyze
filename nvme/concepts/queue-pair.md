# 队列对（Queue Pair）

## 一句话说明

NVMe 通过"提交队列 + 完成队列"组成的队列对来在主机和控制器之间传递命令与完成通知，管理队列管控制，I/O 队列跑数据。

## 生活化类比

把队列对想成**餐厅的点单-上菜两条流水线**：

- **提交队列** = 服务员把顾客的点菜单放进去的托盘架。
- **完成队列** = 厨房出菜口把"已上齐"的牌子放回的托盘架。
- **门铃寄存器** = 服务员按的"催菜铃"，提醒厨房有新单。
- **阶段标签（Phase Tag）** = 牌子上贴的"今日/昨日"贴纸，厨师翻面表示"新一批出菜"。
- **管理队列 vs I/O 队列** = 前台只处理订位/结账（管理类），包厢专门上菜（I/O 类）。
- **Fabrics 队列对** = 外卖平台：每次点单封成"胶囊"发出去，不存在固定的托盘架。

## 工作流程

```text
  主机                 提交队列(SQ)         控制器          完成队列(CQ)
   |  写命令条目 -------->|                  |                 |
   |  按门铃(doorbell) -->|----------------->|                 |
   |                     |    解析+执行      |                 |
   |                     |                  |--- 写完成条目 -->|
   |<---------- MSI-X 中断 / 轮询 CQ --------------------------|
   |                                              ^ 阶段标签翻转
   |  按完成队列头部门铃  <-----------------------| (新条目信号)

  内存模型：多个 SQ 可共享一个 CQ（多对一）
  Fabrics 模型：每个 SQ 必须一对一绑定一个 CQ
  管理 SQ 永远一对一绑定管理 CQ（队列 ID = 0）
```

## 初学者案例

**场景：`nvme create-ioq` 报"Invalid Queue Size"，盘却不忙。**

1. 你写了一个用户态驱动，调用 `nvme_create_io_q` 时传了 `queue_size = 1`。
2. 控制器返回 `Invalid Queue Size`（完成状态 `02h`）。
3. 看规范 3.3.1.3：**队列最少 2 个槽位**，且因为"单槽位未使用"判满规则，**实际可用槽位 = size - 1**。
4. 改成 `queue_size = 64`（或读 `CAP.MQES` 取最大支持值再减一）后重建，正常。
5. 顺手用 `nvme get-feature -f 0x07`（队列数量特性 `07h`）查控制器实际分配了几对 I/O 队列，如果创建数超过分配数也会失败。

> 排错提示：失败时先看 `nvme id-ctrl` 的 `MQES`（最大队列条目数 0-based）和 `CQR`（是否要求连续），再决定 size。

## 必须记住的规则

| 规则 | 要点 |
|------|------|
| 队列 ID | 管理队列固定 0；I/O 队列 1~65535 |
| 队列大小 | 16 位 0-based 槽位数；最少 2；I/O 最大 65536，受 `CAP.MQES` 约束；管理队列上限 4096 |
| 单槽未使用 | 头+1 == 尾即"满"，可用槽位 = size - 1，避免满/空歧义 |
| 创建顺序 | 必须先建 CQ，再建 SQ；删除顺序相反 |
| 内存模型映射 | 管理 SQ/CQ 严格 1:1；I/O SQ 可多对一共享 CQ |
| Fabrics 模型映射 | 每个 I/O SQ 1:1 绑定 CQ，不支持共享 |
| 队列数特性 | Feature ID `07h`（Number of Queues），0-based；任何 I/O 队列存在后改此特性报"命令序列错误" |
| 中断合并特性 | Feature ID `08h`，仅对 I/O 队列生效；时间阈值/计数阈值任一为 0 表示立即中断 |
| 中断向量特性 | Feature ID `09h`，可针对单 I/O 中断向量关闭合并；管理 CQ 永不合并 |
| 完成关联 | CQ 条目带 SQ ID + Command ID，乱序到达也由主机自己匹配 |
| 阶段标签 | CQ 每环绕一次翻转；主机无需读寄存器即可识别"新条目" |
| 执行顺序 | 除融合操作外，控制器可任意顺序消费 SQ 内 / 跨 SQ 命令；优先级属 SQ，不属单条命令 |

## 容易混淆的地方

| 容易混 | 实际区别 |
|--------|----------|
| SQ vs CQ | SQ 装命令条目（主机写→控制器读）；CQ 装完成条目（控制器写→主机读） |
| 头部门铃 vs 尾部门铃 | 主机敲 SQ 尾门铃"有新单"；敲 CQ 头门铃"这条已读" |
| 内存模型 vs Fabrics 模型 | 前者靠门铃寄存器+共享内存；后者靠传输胶囊+连接，无门铃 |
| 队列优先级 vs 命令优先级 | 优先级挂在 SQ 上，作用在仲裁；单条命令无优先级字段 |
| CAP.MQES vs 实际 size | MQES 是 0-based 最大支持槽位数；size 必须 ≤ MQES+1 |
| CSTS.CFS vs CSTS.RDY | CFS=1 表示控制器致命错误；RDY=1 表示已就绪可接受命令 |

## 进阶细节

- **创建步骤（内存模型，规范 3.3.1.1）**：配置 AQA/ASQ/ACQ → 设 `CC.IOSQES`/`CC.IOCQES` → Set Features `07h` 分配队列数 → 读 `CAP.MQES`/`CAP.CQR` → Create I/O CQ → Create I/O SQ。
- **循环缓冲区状态判断**（规范 3.3.1.4/5）：空 = 头==尾；满 = (尾+1) mod size == 头；部分满 = 其他。
- **PRP/SGL 提交阶段**：主机在写完 SQ 条目后**必须**敲尾部门铃；CQ 端完成条目发布后**必须**翻转 Phase Tag。
- **门铃写错值**：触发"非法门铃写入值"异步事件，受影响队列随后被删除重建（规范 3.3.1.2）。
- **Fabrics Connect 命令**（规范 3.3.2）：在已建立的传输连接上发一次，重复 Queue ID 报"命令序列错误"；成功才创建 SQ + CQ。
- **Fabrics Disconnect**：是 SQ 上最后被处理的命令，其响应是 CQ 上最后被消费的条目，形成"提交屏障"（规范 3.3.2.4）。
- **Fabrics 流量控制**（规范 3.3.2.2）：默认启用，控制器在响应胶囊里回 `SQHD`；仅当主机置 `DISSQFC=1` 且控制器回 `SQHD=FFFFh` 时禁用。
- **致命错误**：提交到满的 SQ，或禁用流量控制时未完成命令数 ≥ SQ 大小，会设 `CSTS.CFS`、终止关联。
- **队列级别重置**（规范 3.3.3）：本质是删后重建；内存模型下共享 CQ 要先删所有关联 SQ 才能删 CQ。
- **影子门铃（Shadow Doorbell）**：准虚拟化控制器优化，主机写影子页+事件索引，按 `DSTRD` 跨距交错 SQ 尾/CQ 头（规范 3.3.1.6）。
- **PCIe 队列存储**：CQ 用 PRP 指向主机内存，PRP 列表在删除前必须保持稳定；CMB 放置需 `CMBLOC.CQPDS=1`。
- **未定义行为**：主机在控制器消费前改 SQ 条目 / 在发布后改 CQ 条目，均未定义。
